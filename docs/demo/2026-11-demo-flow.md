# 2026-11 全功能演示：执行流程（录制台本）

本文是演示视频的**操作台本**：按时间码写清每一步点哪里、输入什么、画面应出现什么、异常怎么处理。
配套口播见 [`2026-11-demo-narration.md`](./2026-11-demo-narration.md)；历史版流水线说明见
[`README.md`](./README.md) 与 [`FULL_DEMO_FLOW.md`](./FULL_DEMO_FLOW.md)。

覆盖范围：

1. 代理律师：稀疏提问 → 案情澄清 → 补充事实 → 续跑 → 终答（含多轮会话）
2. 律师助理：起诉状、答辩状各一份（字段预览 → 确认 → Word/PDF 下载）
3. 监控模式：运行列表、统一审计四张结论卡、执行时间轴、证据链、上下文矩阵、性能与异常、节点抽屉、深链
4. 历史记录：列表、抽屉内容、导出 JSON、手动输入会话 ID 恢复、URL 恢复

时间码按**不剪切的实时录制**估算（约 15 分钟）。若成片压到 12 分钟，只需在剪辑时把两段模型等待
（2:10–4:00、5:20–6:30）做 1.5–2 倍速，口播不动。

## 0. 录制前置

### 0.1 启动服务

仓库根目录，两个终端：

```bash
# 后端（仅本机；Windows + PostgreSQL 必须指定 selector loop）
F:/Anaconda_env/lawApp_LangGraph/python.exe -m uvicorn \
  lawApp_LangGraph.FastAPI.api:app --host 127.0.0.1 --port 8000 \
  --loop lawApp_LangGraph.FastAPI.loop:selector_loop_factory

# 前端
cd frontend
npm run dev -- --host 127.0.0.1 --port 5173
```

浏览器打开 <http://127.0.0.1:5173>。前端统一走 Vite 代理的 `/api/...`；后端直连路由**没有**
`/api` 前缀，用 curl 验证时不要加（`/api/...` 会 404）。

### 0.2 就绪检查（录前 1 分钟）

```bash
# 1) 后端可用（该应用没有 /health，用监控列表当探针）
curl -s -o /dev/null -w '%{http_code}\n' \
  "http://127.0.0.1:8000/monitor/runs?limit=1"        # 期望 200

# 2) RAG 预热完成（模型加载实测约 153s，未完成时首轮检索会明显变慢）
grep "RAG 后台预热结束" logs/system.log | tail -1
```

同时在浏览器确认：

- 左栏显示「历史记录」列表（不是「暂无历史」）；
- 右上「监控 →」可点开，运行列表有数据；
- 首次进入若弹「免责声明」，点「我知道了」再开始录。

### 0.3 画面与输入

- 窗口 1440×900（与旧成片一致），浏览器缩放 100%，隐藏书签栏；
- 中文输入法关闭英文联想；长文本一律**粘贴**，不要现场逐字打；
- 录制时不要露出 `.env`、终端里的 Key、数据库口令；
- 每一幕开始前点「新建会话」，确认顶部显示「会话: (新建)」。

### 0.4 每幕重置

| 场景 | 操作 | 校验 |
|------|------|------|
| 换一幕 | 左栏「新建会话」 | 顶部「会话: (新建)」，消息区清空 |
| 换模式 | 点顶部另一模式（自动新建会话） | 顶部「会话: (新建)」，输入区形态切换 |
| 抽屉/弹窗 | 点遮罩、右上 ✕ 或按 Esc | 抽屉/下载弹窗关闭 |
| 完全重来 | 刷新页面后点「新建会话」 | URL 无 `?session=` |

## 2. 代理律师：稀疏提问 → 澄清 → 补充 → 终答

### 2.1 开场（0:00–0:45）

**操作**

1. 停在对话页，不动鼠标 2 秒，让观众看清整体布局。
2. 鼠标依次掠过：顶部「代理律师 / 律师助理」→ 左栏「历史记录」→ 右上「监控 →」。
3. 不点开任何弹窗。

**画面应出现**

- 顶部：模式切换、`会话: (新建)`（或上次的会话 ID）、「监控 →」；
- 左栏：「历史记录」「新建会话」、会话 ID 输入框 +「恢复」、会话列表；
- 中间：代理律师输入框（占位「输入法律咨询问题, 回车发送」）与发送按钮；
- 右下角输入区上方状态栏显示「就绪」。

**口播锚点**：开场定位（见口播 0:00–0:45）。

### 2.2 稀疏提问（0:45–1:20）

**操作**

1. 确认处于「代理律师」模式。
2. 在输入框输入：`我想离婚`
3. 按 Enter。

**画面应出现**（约 2 秒内）

- 用户气泡「我想离婚」，助手气泡进入流式；
- 右侧/下方出现**案件要素面板**，多数要素为黄色「待补齐」；
- 随后弹出琥珀色卡片，标题「案情澄清」，徽标「第 1/5 轮」。

澄清卡内容（实测，模型可能同义改写）：

> 您和对方目前是已经登记结婚、正在共同生活，还是已经分居了？这直接关系到离婚的途径和财产、子女问题的处理方式。

选项：

- A 已登记结婚，目前共同生活
- B 已登记结婚，目前分居
- C 只办了婚礼，没领结婚证
- 其他（请输入）

**讲解点**：系统没有直接给“离婚怎么分房”的泛泛答案，而是先补齐决定法律路径的事实；这一步是
`interrupt()` 落图状态，不是前端假等待。

### 2.3 澄清卡讲解（1:20–2:10）

**操作**

1. 鼠标依次指 A/B/C 三个选项（不提交）。
2. 指一下「第 1/5 轮」徽标与「其他（请输入）」。
3. 不做别的点击。

**口播锚点**：为什么先问婚姻状态；五轮上限；选项来自后端载荷。

### 2.4 补充事实（2:10–2:35）

**操作**

1. 点选「其他（请输入）」。
2. 展开的输入框（占位「请输入其他内容」）中粘贴下面整段：

```text
已登记结婚，是合法夫妻。2016年登记，婚后共同出资买房，登记在丈夫名下。我想离婚并分割房产，孩子5岁由我直接抚养，丈夫按月支付抚养费。手头有结婚证、购房转账记录、微信聊天记录。他同意离婚，但坚持房产一人一半，也争孩子抚养权。
```

3. 点「提交」。

**画面应出现**

- 琥珀卡收起，用户侧出现一条 HITL 回答消息（头部带所答问题摘要）；
- 助手新气泡开始流式，状态栏从「思考中」切到「正在规划检索策略」。

**说明**：选择题提交的是**选项文本**（“其他”时是补充输入），不是字母 A/B/C。这条路径已实测：
补充内容原样进入状态，后续正常续跑。

### 2.7 备选：两轮选项澄清（实测，增加约 90 秒）

如果想把“多轮”拍得更明显，第一张卡直接选 B，第二张卡再用「其他」补充：

1. 第一张卡选 `B 已登记结婚，已分居`，点「提交」；
2. 约 2 秒后出现第二张卡（第 2/5 轮）：

   > 您这次离婚，最核心想解决的是哪件事——是解除婚姻关系本身，还是同时要处理财产分割、
   > 孩子抚养，或者对方存在过错想主张赔偿？

   选项：A 只想尽快解除婚姻关系 / B 要一并分割夫妻共同财产 / C 要争取孩子抚养权 /
   其他（请输入）。
3. 选「其他（请输入）」，粘贴与 2.4 相同的整段事实，提交；
4. 随后进入续跑，产出终答。

**实测基线**：会话 `AT-20261109-123835-012`，三段 run 链
（`123835987688` interrupted → `123838323989` interrupted → `123840310051` ok），
续跑 20 阶段、196.4s、终答 4166 字、5 个工具、4 条引用、2 轮澄清。
比主路线多一轮澄清，剪辑时对执行段做 2 倍速即可。

### 2.5 续跑执行链（2:35–4:40）

**操作**：不点击，让流程自然跑完（实测约 101 秒）。

**画面应出现**

- 计划步骤逐条出现；
- 工具调用依次出现（实测 6 个）：

| 顺序 | 工具 | 作用 |
|------|------|------|
| 1 | `retrieve_legal_knowledge` | RRF 混合检索（稠密 + BM25 + 重排） |
| 2 | `evaluate_case_relevance` | 三档相关性评估 |
| 3 | `fetch_laws` | 法条检索 |
| 4 | `get_google_search` | 网络补充 |
| 5 | `analyze_legal_issue` | 法律分析 |
| 6 | `save_to_memory` | 写入长期记忆 |

- 思考过程逐字流式展开；状态栏经过「正在调用工具 → 质量门控 → 组装最终回答」；
- 终答开始打字机输出。

**口播锚点**：续跑不是重跑；父子 run；检索质量三档；资料不足才联网。

### 2.6 终答与要素（4:40–5:20）

**操作**

1. 展开助手气泡下方「思考过程」，滚动两屏。
2. 指一下要素面板：7 项均变为绿色「已明确」。
3. 指终答标题与「参考材料」。

**实测终答**（3398 字）结构：

```text
# 离婚路径、房产分割与抚养权主张分析
## 一、局势诊断
## 二、法律定性与核心结论
## 三、房产分割：对方“一人一半”不是铁律
## 四、抚养权：5岁孩子的裁判逻辑
## 五、抚养费：按月支付的标准
## 六、“金式战略”：下一步具体行动
## 七、心理锚定
## 参考材料
```

**本幕基线**：会话 `AT-20261109-114422-006`，续跑 run `114424213517`，23 阶段，100.6s，
综合分 82，6 个工具；会话详情引用 6 条，审计聚合引用 18 条（口径不同，见第 5 节）。
录制当次会生成新 ID，数值以现场为准。

## 3. 律师助理：起诉状（5:20–7:20）

### 3.1 切模式并粘贴案情（5:20–5:45）

**操作**

1. 点顶部「律师助理」。
2. 确认顶部「会话: (新建)」，输入区出现「起诉状 / 答辩状」两个 pill 与长文本框。
3. 点「起诉状」pill（默认已选，点一下让高亮可见）。
4. 粘贴完整案情（338 字，实测原文）：

```text
原告李某，女，1985年3月12日出生，汉族，住北京市朝阳区某路12号。被告王某，男，1983年7月8日出生，汉族，住北京市朝阳区某路12号。双方2010年5月登记结婚，2015年6月生育一子王某甲。被告自2020年起与案外人张某保持不正当男女关系，2023年3月擅自将夫妻共同存款50万元转至其母账户，2024年1月起搬离共同住所与张某同居，未支付子女抚养费。原告现起诉离婚，请求：1.判令离婚；2.婚生子由原告直接抚养，被告每月支付抚养费3000元至独立生活止；3.依法分割夫妻共同财产（朝阳区房产一套、存款80万元、车辆一台）；4.被告支付精神损害赔偿5万元。证据：结婚证、出生医学证明、微信聊天记录、银行流水、房产证、车辆登记信息。被告不同意离婚，也不同意孩子归原告。
```

5. 按 `Ctrl + Enter`（或点「发送」）。

**画面应出现**

- 用户气泡为整段案情（超过折叠阈值时显示折叠）；
- 助手开始规划与检索；约 20 秒后弹出「Word 文书生成」确认卡。

### 3.2 字段预览与确认（5:45–6:30）

**画面应出现**

- 确认卡标题「Word 文书生成」；
- 文案：`即将生成 Word 文书(民事起诉状（离婚纠纷）)。已填 38 项, 待补充 36 项。确认生成吗?`
- 下方可滚动字段表，共 74 行：已填字段黑色，待补充字段灰色；关键缺失项带「⚠ 待补充」；
- 按钮：「确认」（发送选项值「确认」）与「跳过」。

**操作**

1. 在字段表滚动 2–3 屏，停在「原告联系电话 / 代理人姓名」等灰色行。
2. 点「确认」。

**画面应出现**

- 全屏「正在生成 Word 文书…」遮罩（文案「按模板填充字段, 请勿关闭页面」）；
- 约 10–15 秒后遮罩消失，弹出「文书已生成」模态：
  - 文件名（如 `起诉状_AS-....docx`）；
  - 「内容由 AI 生成, 需执业律师复核后使用」；
  - 按钮「下载 Word」「下载 PDF」「关闭」。

### 3.3 下载与展示（6:30–7:20）

**操作**

1. 点「下载 Word」，浏览器完成下载；弹窗**不会关闭**，方便继续下载另一种格式。
2. 点「下载 PDF」；首次转换约 15 秒，期间按钮无进度，不要连点。
3. 打开刚下载的 Word：展示标题「民事起诉状」、当事人段、诉讼请求、事实与理由、证据清单、落款。
4. 打开 PDF，展示页数与排版（实测 3 页）。
5. 点「关闭」收起弹窗。

**实测基线**

| 项 | 值 |
|----|----|
| 会话 | `AS-20261109-113700-003` |
| 首轮 run | `113701075795`，11 阶段，20.2s，停在 docx_confirm |
| 续跑 run | `113725734244`，5 阶段，14.6s，`ok` |
| 终答 | 1271 字 |
| Word | 15,245 字节 |
| PDF | 244,486 字节，3 页 |
| 审计链 | 父 11 阶段 + 子 5 阶段，人工等待 4,466ms |

## 4. 律师助理：答辩状（7:20–9:05）

### 4.1 新建并粘贴（7:20–7:45）

**操作**

1. 左栏「新建会话」，确认「会话: (新建)」。
2. 点「答辩状」pill。
3. 粘贴答辩状案情（404 字，实测原文）：

```text
原告周某，女，1987年4月出生，汉族，住北京市海淀区某路8号。被告陈某，男，1985年9月出生，汉族，住北京市海淀区某路8号。原告起诉要求离婚，婚生子陈某甲由原告抚养，被告每月支付抚养费4000元，并分割海淀区房产一套及存款60万元，另主张被告支付精神损害赔偿8万元。被告答辩意见：不同意离婚，双方2013年登记结婚，2016年生育一子，婚后感情基础良好；原告所称被告家暴不属实，2025年3月双方因家庭琐事发生争执，被告未实施殴打，原告提供的照片不能证明伤情来源；被告从未转移夫妻共同财产，存款60万元中20万元用于孩子教育培训，40万元仍在共同账户；房产系被告婚前首付、婚后共同还贷，分割时应考虑被告贡献；被告有稳定工作和住所，孩子一直由双方共同照顾，若法院判决离婚，被告也要求直接抚养孩子，并愿意承担抚养费。证据：结婚证、房产证、贷款合同、银行流水、孩子学校证明、被告单位收入证明、双方微信沟通记录。
```

4. `Ctrl + Enter`。

### 4.2 确认与生成（7:45–8:35）

**画面应出现**（约 20 秒后）

- 确认卡：`即将生成 Word 文书(民事答辩状（离婚纠纷）)。已填 21 项, 待补充 20 项。确认生成吗?`
- 字段表共 41 行；与起诉状模板不同的字段（案号、答辩人工作单位/职务等）为灰色；
- 点「确认」→ 生成遮罩 → 「文书已生成」。

### 4.3 下载与对比（8:35–9:05）

**操作**

1. 下载 Word，打开展示「民事答辩状」的答辩人信息、答辩意见分点、证据与落款。
2. 下载 PDF，展示 2 页排版。
3. 口播点出与起诉状的差异：模板不同（41 vs 74 字段）、行文立场不同（答辩 vs 起诉）。

**实测基线**

| 项 | 值 |
|----|----|

| 续跑 run | `113832315548`，5 阶段，13.2s，`ok` |
| 终答 | 1495 字 |
| Word | 13,720 字节 |

**画面**：四张卡「流程 / 证据链 / 上下文 / 性能」，每张右上角是等级标签（通过 / 注意 / 异常 / 未知），

**实测（起诉状会话）**

|----|------|------|
| 流程 | 注意 | 流程完成但发生过回环/重试 |

| 上下文 | 注意 | 上下文有预算截断 |

**讲解点**：「注意」不等于失败。一次重试、一次预算截断都会如实标黄，审计不粉饰。

### 5.3 执行时间轴（10:20–11:00）

**画面**：标题「执行时间轴 N 组 / M 阶段」；起诉状为 `13 组 / 16 阶段`，代理律师先生成的那条为
`16 组 / 27 阶段`。

**操作**

2. 指 `hitl` 分组「澄清反问」上的状态 `interrupted`，以及后面的 `ok`。
3. 点一个 `tools` 步骤，打开右侧节点抽屉（下一节细讲）。

**口径**：组是“一次决策/一步执行”的聚合，阶段是节点级执行行；两者数量不同是正常的
（executor、tools、merge 会同属一个 step 组）。

### 5.4 节点抽屉（11:00–11:50）

**操作**：依次点 6 个 tab，每个停 3–5 秒：

| tab | 展示内容 | 讲解点 |
|-----|----------|--------|
| 概览 | 阶段号、状态、耗时、路由 `→ xxx`、证据/引用计数、上下文标记 | 一眼看节点干了什么 |
| 决策 | 路由理由、决策摘要、计划步骤与重试 | 为什么走这条边 |
| 证据 | 本节点产出/消费的工具结果、文档、引用、缺口 | 答案依据从哪来 |
| 上下文 | 7 段上下文（任务/提问/要素/历史/证据/约束/记忆）与继承、截断标记 | 模型当时看到了什么 |
| 调用 | LLM/工具 span、耗时、tokens | 钱花在哪 |
| 原始数据 | 按需加载的原始 JSON | 默认不拉，避免大 payload 与敏感内容 |

**注意**：「原始数据」可能含完整案情与内部 prompt，录制时不要展开敏感字段，口播说明“按需加载”即可。

**深链**：选中节点后地址栏会带上
`/monitor#run=<run_id>&stage=<stage_id>&tab=<tab>`，复制到新标签页可复原同一节点与 tab。

### 5.5 证据链（11:50–12:10）

**画面**：证据链板分四块——工具调用、文档、引用、缺口。

**实测（代理律师会话 `AT-20261109-114422-006`）**

- 工具调用 6 条；文档 24 篇；引用 18 条；缺口 10 条；

- 点缺口行或「定位」跳到对应阶段。

**讲解点**：结论卡说“证据链注意”，不是否定引用，而是指出有文档没进入分析，属于可改进项。

### 5.6 上下文矩阵与性能（12:10–12:45）

**上下文矩阵**（同一会话）

- 7 个段：任务、提问、要素、历史、证据、约束、记忆；
- 27 个节点、22,794 字符；`evidence` 段被预算截断（图例 `! 截断`，`↳` 表示继承上游）；
- 点任一节点跳到其抽屉的「上下文」tab。

**性能与异常**

**讲解点**：人工等待是审计里单独一列，不和模型执行混在一起；这次脚本补充等待只有 0.15s，
真人演示会更长，但链路一致。

## 8. 失败预案

| 现象 | 原因 | 处理 |
|------|------|------|
| 聊天出现 `出错: Connection error.` | LLM 提供方网络瞬断 | 不做兜底是设计；重发同一问题，先确认外网/额度正常 |
| `出错: … (不做兜底, 请修正后重试)` | 请求校验/连接失败 | 看后端 `logs/system.log` 对应 4xx/5xx，修正后重试 |
| PDF 502「尚未调用 CoInitialize」 | 后端还是旧进程（缺 COM 初始化修复） | 重启后端，确认代码含 `pythoncom.CoInitialize()` |
| PDF 502「需本机安装 Microsoft Word」 | 无 Word/COM 不可用 | 安装 Word 或改用 Word 下载演示；不要口播“PDF 一定可用” |
| PDF 下载很慢（>15s） | Word COM 冷启动 | 正常，转换上限 90s；不要连点 |
| 监控显示「部分可审计」 | 旧 run 缺证据/上下文/tokens 采集 | 选刚跑的新 run；旧 run 只做历史对照 |
| 监控列表为空/降级 | PostgreSQL 不可用 | 先修数据库连接，再录监控；不要用假数据 |
| 历史列表「暂无历史」 | 会话登记失败/后端未连库 | 查 `logs/agent_flow.log` 的「会话列表降级」 |
| 恢复会话失败 | ID 输错或会话不存在 | 从列表复制完整 ID，区分 `AT-`/`AS-` 前缀 |
| 提交后 409 | 同会话已有流在跑 | 等当前流结束再提交；不要并发双击 |
| 首轮检索特别慢 | RAG 未预热完 | 等 `logs/system.log` 出现「RAG 后台预热结束」再录 |
