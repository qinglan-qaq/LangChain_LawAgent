## 1. 旧版结构（2026-11-06）

旧版按 6 个 Act 组织，约 11–12 分钟：

| 时间 | Act | 主题 |
|------|-----|------|
| 0:00–0:50 | Act 0 | 开场：双模式、会话列表、监控入口 |
| 0:50–2:20 | Act 1 | 安全闸门：高风险问题 → `risk_confirm` → 中止并给求助热线 |
| 2:20–5:30 | Act 2 | 主链路：完整案情 → 要素澄清 → 5 步执行 → 终答 |
| 5:30–6:40 | Act 3 | 检索深挖：RRF / CrossEncoder / CRAG 三档 |
| 6:40–9:00 | Act 4 | 文书交付：74 字段预览 → `docx_confirm` → Word |
| 9:00–10:30 | Act 5 | 可观测/质量：监控时间轴、评测、pytest |
| 10:30–11:20 | Act 6 | 收尾：方法论与边界 |

当前主台本改成了五个连续场景：代理律师多轮 → 起诉状 → 答辩状 → 统一审计 → 历史恢复。
高风险闸门仍存在于代码中，但它不是本次演示主线；如要现场展示，需先按当前构建重新验证触发句与选项。

## 2. 旧版中已失效的结论

### 2.1 「必须用 Docker 新建演示库」

旧版假设本机 PostgreSQL 密码校验失败，要求 `docker run` 一个 15433 端口的演示库。
当前环境直接使用**本机既有 PostgreSQL**，不新建库、不新建表；`sessions / trace_runs / trace_spans /
stage_chain / minor_states` 等表由后端启动时幂等建好。录制前只需确认：

```bash
curl -s http://127.0.0.1:8000/home
# 期望包含 "checkpoint_backend":"postgres"
```

不要按旧版修改 `.env` 的端口/密码，也不要把数据库口令贴进录制画面。

### 2.2 「`element_fill` 递归上限，文书段不可录」

旧版把 `Recursion limit of 60 reached` 当成未修阻塞，并建议「文书段改用预录素材」。
当前 `request_element_fill` 在过滤后无缺口时已推进 `current_step_index`，起诉状与答辩状都实测走到
`docx_confirm` 并生成 Word/PDF。不要再按旧版「已知阻塞」跳过文书段，也不要现场打补丁。

### 2.3 「聊天页没有 PDF 按钮，PDF 只能走 `/ask/pdf`」

旧版称前端只渲染 docx 下载，PDF 终答与工具结果矛盾。当前 `DocReadyModal` 同时提供
「下载 Word」与「下载 PDF」，后端 `/sessions/{sid}/doc/pdf` 已修复 Word COM 线程初始化
（`pythoncom.CoInitialize()` / `CoUninitialize()`），起诉状 PDF 244,486 字节 / 3 页、答辩状 PDF
223,210 字节 / 2 页均实测 200。PDF 仍依赖本机 Microsoft Word，首次转换约 15 秒、上限 90 秒；
无 Word 时不要口播「PDF 一定可用」。

### 2.4 「监控页无数据，只能讲代码」

旧版把监控当作「PG 恢复后才能补录」。当前 `/monitor` 已有运行列表、统一审计四结论卡、父子 run 链、
执行时间轴、证据链、上下文矩阵、性能面板与节点抽屉；录制时直接用刚跑出的 run 即可。

## 3. 仍可参考的内容

- **检索参数**：`RRF_K=60`、`CORRECT_THRESHOLD=0.731`、`INCORRECT_THRESHOLD=0.5005`，
  以 `config.py` 与页面实际值为准。口播口径仍是「阈值由 30 条分层案例标定」，不要承诺未验证的提升比例。
- **8 类 HITL 对照**：`clarify / mid_clarify / field_clarify / risk_confirm / degrade_confirm /
  budget_confirm / docx_confirm / pdf_confirm`。当前演示现场覆盖 `clarify`、`docx_confirm`；
  其余类型以代码与历史 run 为证据，不要假装现场触发。
- **检索质量叙事**：双路召回 → RRF 只按名次融合 → CrossEncoder 绝对分 → 三档判定 → 不足则降级联网。
  这段解释仍适用于当前主链路，可放进代理律师续跑段的旁白。
- **失败预案思路**：模型超时重试、外部检索不可用不现场切后端、Word 缺失不硬演 PDF、监控无数据不造假。
  当前可执行版本已整理到新台本第 8 节。

## 4. 旧版红线（已更新）

1. PostgreSQL 必须真实可用才讲「checkpoint / 续跑 / 历史恢复」；当前基线是 `postgres`，不是 `inmemory`。
2. 不讲未验证的降本比例；双模型分层是事实，具体收益以 trace token 为准。
3. 不讲「74 字段全部自动填满」；讲「74 字段模板，已填/待补可见，律师确认后生成」。
4. PDF 可以讲，但要说明依赖本机 Word、首次转换较慢；无 Word 时只演示 Word。
5. 不讲客户/律所规模数据；演示案情均为虚构，导出文件含 PII、只留本机。
6. 监控是执行追踪与审计回放，不是实时告警/APM。
7. 所有输出是辅助材料，最终由执业律师复核，不构成法律意见。
